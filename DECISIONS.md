| DEC-001 | 2026-09-07 | Adopt Angular (NgModules) + Tailwind CSS frontend, Spring Boot (Java/Maven) backend, PostgreSQL database — modernizing away from THESIS1's Visual Basic 2010/Microsoft Access stack rather than replicating it | Accepted | Mirrors the vault's standard E-Commerce backend architecture pattern. Not reopened in later revisions of `docs/project-initiation-draft.md`. |
| DEC-002 | 2026-09-07 | Use Spring Security + JWT + Bcrypt password hashing, uniformly across Manager/Employee/Owner roles | Accepted | Replaces raw credential storage assumed in THESIS1. Directly corrects THESIS3's own internal inconsistency (MD5 for User/Admin, bcrypt for Mechanics) rather than inheriting it. |
| DEC-003 | 2026-09-11 | Treat all three source theses (THESIS1: AJ Trading Motorparts, THESIS2: Mr. Siklo, THESIS3: Spares Mart) as reference patterns only — never copy a data dictionary, payment scope, or security approach as-is | Accepted | THESIS1's schema has FK copy-paste drift; THESIS2 has no extractable table-level dictionary; THESIS3 is OCR-corrupted and contains two confirmed-unrelated boilerplate subsections (crime-reporting, book-rental). The ChardWorkz schema is designed fresh from real business rules. Confirmation from the business owner still sought as Q6. |
| DEC-004 | 2026-09-11 | Reject THESIS2's mobile-admin limitation ("no mobile admin, all admin desktop-web-only") as an anti-requirement for ChardWorkz | Accepted (pending final confirmation) | A ChardWorkz manager must be able to approve stock-in and read reports from a phone. One responsive Angular codebase serves all roles at every breakpoint (counter desktop / staff tablet / phone) — no role is locked to a single device class. Final confirmation sought as Q11. |
| DEC-005 | 2026-09-11 | Model `stock_level` as its own entity keyed by `product_id` + `branch_id`, separate from `product` identity | Accepted | THESIS1's schema kept quantity on the product row directly, which cannot represent two branches with independent stock counts. ChardWorkz has two real branches (main + Masinag), so this split is made from Phase 0 regardless of how Q5 (branch sync behavior) is eventually answered. |
| DEC-006 | 2026-09-11 | Represent payment as a `payment_method` enum (`CASH`, `GCASH`, `EWALLET_OTHER`) plus an optional reference number, with any real gateway integration built as a separate pluggable `PaymentGateway` port | Accepted | Absorbs THESIS1 (cash-only), THESIS2 (GCash-only), and THESIS3 (card/UPI/net-banking fields, no shipped gateway) into one schema without committing to a specific gateway. Phase 1 payment confirmation stays manual at the counter until Q4 is answered. |
| DEC-007 | 2026-09-11 | Reserve `branch_id` (all transactional tables), `payment_method` (as an enum, not a boolean), and `sku`/`barcode` (on product) from Phase 0, even though the behaviors they support (multi-branch sync, payment gateway, barcode scanning) are all still open or deferred | Accepted | These columns are cheap to add at schema-design time and expensive to retrofit onto a live system. Reserving them does not commit to building the feature — see Q4, Q5, and the Out-of-Scope table in `docs/project-initiation-draft.md` §1. |
| DEC-008 | 2026-09-11 | Model the powder-coating service as a `Job` entity (intake → assign technician → status → price), generalized from THESIS3's Mechanics module, rather than forcing it into the `Product` model | Accepted (conditional on Q2) | None of the three source theses model a service/labor business; THESIS3's Mechanics module (provider profile, availability, booking, pricing, reviews) is the nearest structural analog. Whether the Job module ships at all — Phase 3B — depends on Q2, which is still open. |
| DEC-009 | 2026-09-11 | Notifications: implement `EmailSender` via Spring Mail now; define `SmsSender` as an interface with no implementation in Phase 1 | Accepted | THESIS2 used PHPMailer for order-status/low-stock email; THESIS3 added SMS verification. Email alone covers Phase 1–2 needs (low-stock alerts to the manager); an SMS provider becomes a wiring change later rather than a redesign. Channel scope (customer-facing vs. internal-only vs. both) is still open as Q3. |
| DEC-010 | 2026-09-11 | Keep Q1 (customer-facing storefront vs. staff-only checkout) and Q2 (powder-coating job module) open rather than defaulting either into the committed architecture, even though both materially change the module set | Accepted | Phase 1–2 (staff-only core) proceed unconditionally either way. Phase 3A (storefront) and Phase 3B (job module) are written as separately-attachable, clearly-gated phases in `docs/project-initiation-draft.md` §4 rather than assumed. |
| DEC-011 | 2026-09-11 | Scaffold the six CLAUDE.md-required authority files for this Active project (`PROJECT-CONTEXT.md`, `memory.md`, `handoff.md`, `DECISIONS.md`, `backlog.md`, `README.md`), previously missing or empty | Accepted | Brings ChardWorkz into compliance with the vault's Active-project schema (CLAUDE.md §4). Content is scaled to the project's actual planning-stage maturity — no code or repo exists yet — rather than padded to match a mature project's file sizes. |
