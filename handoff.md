This also stood up frontend HTTP/auth plumbing that didn't exist at all before (`core/auth.ts`, `core/auth-interceptor.ts`, `environments/`) — deliberately **not** a login page or route guard, which stay deferred to the Register task. Server derives `branch`/`employee` from the JWT, never the client payload; totals are recomputed server-side from `quantity × unitPrice`. Oversell (accepted Q12 risk) clamps `stock_level.quantity` at 0 rather than going negative, per the user's explicit choice. Verified live end-to-end in an actual Chrome browser (not just curl) via `claude-in-chrome`: normal sync, idempotent replay, oversell clamp, a real network outage (backend killed) correctly queued the sale and auto-synced within 30 seconds of the backend returning with zero manual action, and a truly invalid sale correctly went to a terminal `FAILED` state instead of retrying forever. Found and fixed two real, previously-latent bugs only because of this live testing: (1) `ResponseStatusException` validation errors were incorrectly returning 401 instead of 400, because the internal `/error` servlet forward wasn't authenticated and Spring's `OncePerRequestFilter` skips `ERROR` dispatches by default — fixed by permitting `/error` in `SecurityConfig`; (2) **the backend had zero CORS configuration**, meaning no browser-based frontend call could ever have reached it at all, regardless of this feature — fixed via a new `app.cors.allowed-origin` env var (blank/no-op in production).
